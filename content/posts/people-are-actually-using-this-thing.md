<p><em>(Or, what 23k downloads and a pile of bug reports taught me about UniFi + Terraform)</em></p><p>Back in May I <a href="/why-i-wrote-a-new-terraform-provider-for-unifi/">wrote about shipping a UniFi Terraform provider</a> because I got tired of clicking through the Network UI for firewall rules and WiFi settings. At the time it had been out for about a week, sitting at ~150 downloads, and I was mostly talking to myself and a couple of Matrix folks.</p><p>That was fine. Shipping something useful for <em>me</em> was the goal.</p><p>Then the downloads kept going up. Then the issues started. Then the PRs.</p><p>As of this week the provider is somewhere around <strong>23,600 downloads</strong> on the Terraform Registry, and more importantly — people I don't know are running it against real controllers and telling me when it falls over. That is the part that actually matters.</p><h2 id="thank-you-sincerely">Thank you, sincerely</h2><p>I want to say this plainly before I get into the technical bits: thank you.</p><p>If you tried the provider, filed an issue with a repro, opened a PR, yelled about a weird float64 drift on 2.4 GHz, or just dropped a note that you were using it — that feedback is the difference between "Sol's homelab module" and "something other people can trust."</p><p>A few shout-outs that deserve more than a buried changelog line:</p><ul><li><strong><a href="https://github.com/thewhit">thewhit</a></strong> — Enterprise (802.1X) WiFi, WPA2 PPSK, and a configurable HTTP timeout because UniFi can take its sweet time during reprovision. That is the kind of "I hit this in production, here is the fix" energy that makes a provider better overnight.</li><li><strong><a href="https://github.com/dreh23">dreh23</a></strong> — Site Manager / cloud connector base URL fix, plus portable <code>awk</code> so docs generation isn't quietly GNU-awk-flavored. Small PRs. High leverage.</li><li><strong><a href="https://github.com/michaelpeterswa">michaelpeterswa</a></strong> — Bug reports with enough detail that I didn't have to guess. The <code>broadcasting_frequencies_ghz</code> perpetual plan diff, the <code>match_opposite</code> null / inconsistent-result-after-apply mess. Repro-quality issues are a gift.</li><li><strong><a href="https://github.com/hectellian">hectellian</a></strong> — OpenTofu Registry / GPG signing. Reminder that not everyone lives in HashiCorp's world, and that's a good thing.</li></ul><p>Also everyone who opened something and then patiently waited while I dug through controller responses that look nothing like the OpenAPI snapshot. You know who you are.</p><h2 id="what-i-actually-learned">What I actually learned</h2><p>Shipping this against UniFi has been equal parts Terraform provider work and archaeology.</p><p><strong>The OpenAPI is a map, not the territory.</strong> Ubiquiti publishes Integration API docs, and those are useful. Controllers still do their own thing — especially around legacy endpoints, site scoping, and fields that round-trip differently than they went in. Floats for radio frequencies, omitted vs null vs empty for firewall match fields, timeouts that only show up when an AP is mid-reprovision. The provider has gotten better because users ran into those edges, not because I imagined them first.</p><p><strong>Plan-time validation is cheaper than support.</strong> Every time someone hits a confusing apply error that we could have caught at plan, that's a docs/guide/schema gap. I've been tightening that and adding guides (getting started, vs the legacy provider, firewall) so the Registry page is more "operator landing page" and less "here's a schema dump, good luck."</p><p><strong>Relative links on the Registry will humble you.</strong> I shipped docs improvements, cut a release, celebrated, then discovered a pile of 404s because relative paths from <code>/docs</code> (no trailing slash) do not do what you think. Fixed in <code>0.5.5</code>. Classic "works on my machine / GitHub preview" energy.</p><p><strong>People use what is documented for <em>their</em> job.</strong> Homelabbers and folks managing a handful of sites don't care that I think the Integration API path is elegant. They care: auth, site, create a network, put a firewall policy in place, don't break WiFi. The recent overview/guides pass was me listening to that.</p><p><strong>Open source is a conversation.</strong> I can maintain this alone for a while. I cannot cover every controller version, every WiFi enterprise edge case, and every OpenTofu packaging quirk alone. Issues and PRs aren't noise — they're the product roadmap I didn't know I needed.</p><h2 id="sharp-edges-still">Sharp edges (still)</h2><p>Honesty hour, same as the first post:</p><ul><li>Not every Network UI knob is a resource yet. Device naming, switch port overrides, AP groups / device tags — still on the board.</li><li>UniFi moves. OpenAPI snapshots update; behavior drifts; we chase.</li><li>Some bug reports are still open because the right fix is "model the API more carefully," not "slap a lifecycle ignore on it and call it done."</li></ul><p>If you hit something weird, please file it. A config snippet and controller version beats a vague "it doesn't work."</p><h2 id="whats-next">What's next</h2><p>Keep absorbing feedback. Keep fixing the inconsistent-apply class of bugs. Keep the docs aimed at people who just want their network as code without becoming UniFi API experts.</p><p>Registry: <a href="https://registry.terraform.io/providers/BadgerOps/unifi/latest">registry.terraform.io/providers/BadgerOps/unifi</a><br>GitHub: <a href="https://github.com/BadgerOps/terraform-provider-unifi">github.com/BadgerOps/terraform-provider-unifi</a><br>Earlier post: <a href="/why-i-wrote-a-new-terraform-provider-for-unifi/">Why I Wrote a New Terraform Provider for UniFi</a></p><p>If this has been useful in your lab or at work, issues and PRs are welcome. I read them. I learn from them. That's the whole point.</p><p>-BadgerOps</p>
